## 3. 数据库账单实体与金额精度 **[实测]**

### 3.1 现状

| 项目 | 值 |
|---|---|
| `SCHEMA_VERSION` | **1** |
| `MIGRATIONS` | **空** `{}`（无历史迁移步骤） |
| 业务表 | 12 张 |

`bill_record`（第一阶段冻结的账单实体）实际只有 8 列：

```sql
bill_id              TEXT PRIMARY KEY
project_id           TEXT NOT NULL REFERENCES project(project_id) ON DELETE RESTRICT
billing_period_start TEXT
billing_period_end   TEXT
total_energy_kwh     REAL CHECK (total_energy_kwh IS NULL OR total_energy_kwh >= 0)
total_amount_yuan    REAL CHECK (total_amount_yuan IS NULL OR total_amount_yuan >= 0)
validation_status    TEXT NOT NULL DEFAULT 'unvalidated'
source_document_id   TEXT REFERENCES document(document_id) ON DELETE SET NULL
```

领域模型 `domain/models.py::BillRecord` 对应字段类型为 `float | None` **[实测]**。

### 3.2 金额精度问题（**高风险，必须解决**）

**[实测]** 其他表的数值列同样使用 `REAL`：

| 表 | 列 |
|---|---|
| `bill_record` | `total_energy_kwh REAL`、`total_amount_yuan REAL` |
| `load_profile` | `energy_kwh REAL` |
| `pv_model` | `annual_generation_kwh REAL` |
| `result_record` | `value REAL` |

**影响**：

1. SQLite 的 `REAL` 是 IEEE-754 双精度浮点。账单金额（元，两位小数）与
   电量（kWh，整数或一位小数）经浮点存储后再读回，**无法保证十进制精确**，
   费用勾稽（如"五项之和 = 工商业电费"）可能出现分位误差；
2. 现有 `BillRecord` 的 `>= 0` 约束还**禁止负金额**，
   而真实账单存在合法负费用（功率因数调整电费实测为 `-9206.37` / `-37735.81`）**[实测：前一阶段真实账单核验]**；
3. `validation_status` 仅有 `unvalidated / valid / invalid / warning` **[实测]**，
   与本次要求的"待复核 / 已复核 / 存在疑问 / 不适用"四态**语义不匹配**。

**结论**：账单落库必须走 `SCHEMA_VERSION = 2` 迁移，且金额改为十进制安全存储
（整数分或十进制字符串）。**不得**把新账单模型直接塞进现有 `bill_record`。

## 5. PDF/OCR 现有代码的处置建议

### 5.1 耦合度实测 **[实测]**

用 AST 提取各文件的内部依赖，并用全仓库检索确认引用方：

| 文件 | 内部依赖 | 被谁引用（生产代码） |
|---|---|---|
| `domain/pdf_extraction.py` | **无** | 仅 `domain/bill_fields.py`、`infrastructure/pdf/extractor.py` |
| `domain/bill_fields.py` | `domain/pdf_extraction`、`domain/validation` | 仅 `calculations/bill_parsing/parser.py` |
| `infrastructure/pdf/extractor.py` | `domain/pdf_extraction` | **无其它引用** |
| `calculations/bill_parsing/parser.py` | `bill_parsing.numbers`、`domain/bill_fields`、`domain/pdf_extraction`、`domain/validation` | **无其它引用** |
| `calculations/bill_parsing/numbers.py` | **无** | 仅 `parser.py` |
| `ui/main_window.py` | `app`、`application.project_service`、`domain.exceptions`、`domain.models` | — |
| `application/project_service.py` | `calculations.self_consumption`、`domain.*`、`infrastructure.database` | — |

**关键结论**：

1. **PDF 相关代码与目标架构完全解耦** —— `ui` 与 `application` **没有任何**
   对 `bill_parsing`、`pdf_extraction`、`bill_fields`、`infrastructure.pdf` 的引用 **[实测]**；
2. 无 PDF 代码被经济评价链路（消纳计算、项目服务、数据库）依赖；
3. 分层守卫已强制 `pypdf` 只能出现在 `infrastructure` **[实测：`test_pdf_libraries_only_allowed_in_infrastructure`]**；
4. 因此**删除或隔离都不会影响目标架构**。

### 5.2 建议：**保留并隔离，不删除**（分三步）

**不建议立即删除**，理由：

- 代码是一份可工作的、有 166 例测试覆盖的**中文账单文本处理资产**，
  删除即丧失回归能力；
- 删除会改变 `pypdf` 依赖与 4 个测试文件，需重跑大量回归，
  与本轮"不修改业务代码"的要求冲突；
- 法规/审计场景下，"为什么当初做 PDF 又停掉"的可追溯记录有价值。

**建议处置**：

| 步骤 | 动作 | 说明 |
|---|---|---|
| 第一步（文档层，**本轮即可做**） | 在 `README.md`、`PRD.md`、`ROADMAP.md`、`ARCHITECTURE.md`、`docs/phase2/*` 顶部标注：**该能力属于已取消的自动识别路线，保留为实验能力，不再开发，其输出不得直接进入正式测算** | 零代码风险，消除"以为还在做 OCR"的误解 |
| 第二步（隔离层） | 把 `calculations/bill_parsing/` 与 `infrastructure/pdf/` 标注为 `experimental/`（可仅通过文档与模块 docstring 声明，或移入 `src/cenep/experimental/`） | 关键是把"实验代码"与"产品主线"在结构上分开 |
| 第三步（可选，后续按需） | 若确认永不使用，再整体删除并同步清理 `pypdf` 依赖、4 个测试文件与相关文档 | 删除是独立决策，需单独授权 |

**可复用部分（重要）**：`calculations/bill_parsing/numbers.py` 是**纯文本数值解析**
（千分位、括号负数、单位换算、被换行切开的小数、行内空白），
**输入是字符串、输出是 Decimal**，与 PDF 无关 **[实测：该文件无任何内部依赖]**。
Excel 导入同样需要解析单元格中的中文数值文本，**建议直接复用该模块**，
而不是重写一份。

## 6. Excel 模板与导入功能的模块设计（可直接开工）

### 6.1 产品流程冻结

```
人工整理账单数据
  → 填写或导入标准 Excel 模板（7 张工作表）
  → 导入预览（有效 / 警告 / 无效记录）
  → 数据校验（13 类）
  → 人工确认
  → 保存到项目（SQLite）
  → 供经济评价模块使用
```

**明确不包含**：软件内 PDF 自动识别；OCR；依赖 PDF 解析结果自动进入正式测算。

### 6.2 模块划分与分层 **[推断：建议方案，非现状]**

| 模块 | 职责 | 允许依赖 |
|---|---|---|
| `domain/bill_models.py` | 账单六类实体与枚举（纯数据 + 约束） | 标准库、`domain` |
| `data/bill_template_spec.py` | 模板结构规范（工作表/字段/单位/枚举，**纯数据无 Excel 依赖**） | `domain` |
| `data/template_writer.py` | 生成模板文件（openpyxl） | `bill_template_spec` |
| `data/template_reader.py` | 读取 + 表头检查 + 列映射（openpyxl） | `bill_template_spec` |
| `data/bill_validation.py` | 13 类数据校验（纯规则） | `domain` |
| `data/bill_import_service.py` | 预览、错误汇总、重复识别、用户决策、批次记录 | `data` + `domain` |
| `application/bill_service.py` | 编排：导入→校验→确认→保存→查询 | `application` + `domain` + `infrastructure` + `data` |
| `infrastructure/database.py` | `SCHEMA_VERSION = 2` 迁移与新表持久化 | 标准库 `sqlite3` |
| `ui/` | 账单页面（列表/编辑/导入预览/校验结果） | 仅经 `application` |

分层规则（延续既有守卫，新增 `data` 层）：

- `data` **只依赖 `domain`**；`ui` / `application` 通过 `data` 处理表格，
  **界面不得直接操作 Excel**；
- `openpyxl` 只允许出现在 `data` 与 `infrastructure`。

### 6.3 三条必须固化的数据纪律（本次方向的核心价值）

1. **空值 ≠ 0**：未提供的字段存 `NULL`，**不得自动补 0**；
2. **金额精确**：领域层用 `Decimal`，落库用十进制安全格式（整数分或十进制字符串），
   **不再使用 `REAL`**；
3. **未确认不得测算**：`is_usable_for_calculation` 必须同时满足
   "提取/导入完整 + 无缺失冲突 + 勾稽在容差内 + **已人工确认**"。

### 6.4 关于本地已有实现的说明

第 6.2 节的模块设计在**本地未推送提交中已有一份可工作的实现**
（`data/` 四个模块 + `domain/bill_models.py`，本地 702 passed，
模板 7 表齐备、业务表不预置数据行、13 类校验含"缺失视为未知而非 0"）。
该实现可作为开工基础，但**必须先决定其推送/评审方式**（见第 0 节）。

1. **Python 3.14 是官方支持目标**：pvlib 的 CI 矩阵**明确包含 3.14**
   （`pytest.yml` 与 `pytest-remote-data.yml` 均为 `3.11–3.14`）**[实测]**。
   因此 V-a 风险**显著下降**：pvlib 本体为 `py3-none-any` 纯 Python，
   其 CI 在 3.14 上安装依赖并跑通测试，说明上游依赖链在 3.14 上可用。
   **但仍建议在本项目 venv 中实测一次安装**（CI 用的 conda/pip 组合与本地不同）。
2. **离线能力：设计上分离**。存在**独立的** `pytest-remote-data.yml`，
   说明"需要联网的测试"被单独隔离，**常规测试与核心功能不依赖网络** **[实测]**。
   这是 pvlib 适合离线产品的强证据。
3. **`requests` 是核心依赖** **[实测]**，对应 `pvlib.iotools.*` 取数功能。
   离线产品只需**不使用 iotools**，改用本地天气文件即可。
4. **气象数据：pvlib 不自带数据**，只提供读取接口 **[推断，仍需核实具体清单]**。
   离线产品必须**另行获取 TMY 数据**（EnergyPlus/NSRDB/PVGIS 等），
   部分来源需注册或联网 —— 这是**产品化的实际门槛**，也是 V-c 的核心。
5. **依赖重量**：引入 pvlib 等于引入 numpy/pandas/scipy/h5py/requests。
   其中 **pandas 已在项目依赖中**（`pandas>=2.0`，本机实测 3.0.6），
   增量主要是 `scipy`、`h5py`、`pytz`、`tzdata`、`requests`；
   对本地桌面打包可接受，但会增大安装体积。

**适配结论：阶段 4（发电量模拟）采用，需先做两项验证**

| 验证项 | 必须确认的内容 | 风险 |
|---|---|---|
| V-a | 在本项目 venv（Python 3.11 与 3.14）中实测 `pip install pvlib` 并 `import` | **已降低**：pvlib CI 矩阵含 3.14 |
| V-b | 断网环境下用**本地天气文件**跑通核心建模（不使用 iotools） | **已降低**：联网测试被官方隔离 |
| V-c | 气象数据的合法离线获取途径（来源、许可、是否需要注册） | **仍为开放风险** |

**建议用法**：把 pvlib 调用隔离在 `calculations/pv_generation.py`
（或读天气文件时置于 `data`/`infrastructure`），**只向外暴露逐时发电量序列**，
不把 pvlib 对象泄漏到领域层；并保留"自建简化工况模型"作为无 pvlib 时的降级路径。

**未能核实**：`ModelChain` 的当前 API 细节、气象数据读取接口的具体清单、
中国境内气象数据的可获取性 —— 未逐文件阅读 pvlib 源码。
