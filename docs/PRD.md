# CENEP 产品需求说明书（PRD）

- 软件名称：CENEP —— 中国工商业分布式光伏项目经济评价软件
- 当前版本：`0.1.0`
- 当前阶段：第一阶段：工程骨架与核心规则冻结
- 计算规则版本：`CALCULATION_VERSION = "0.1.0"`（`src/cenep/calculations/self_consumption.py`）
- 假设版本：`ASSUMPTIONS_VERSION = "2026.02-stage1"`（`src/cenep/domain/models.py`）
- 运行环境：Windows 上的 Python 桌面应用，要求 `Python >= 3.11`，实际开发与测试环境为 Python 3.14.7
- 配套文档：`docs/CALCULATION_SPEC.md`（计算口径的唯一权威说明）、`docs/ROADMAP.md`（分阶段路线）

本文件描述产品要做什么、做到什么程度、以及当前版本**明确不做什么**。
凡本文件与代码不一致之处，以代码与 `docs/CALCULATION_SPEC.md` 为准。

---

## 1. 产品目标与定位

### 1.1 产品目标

1. 让工商业分布式光伏项目的前期评价过程**可复算、可追溯**：每一次计算结果都能回答"用了哪份输入、按哪版规则算的"。
2. 把光伏消纳这件最容易算错的事，按**逐时段**口径做对：不使用简单年平均电价、不使用年度总量倒推自用率。
3. 明确区分**缺失数据、估算数据与正式数据**，让使用者知道每一份结果的证据等级，而不是拿到一个看似精确的数字。
4. 形成一条从原始台账（电费账单、负荷数据）到评价结论（方案对比、报告）的完整数据链路。

### 1.2 产品定位

| 维度 | 定位 |
|---|---|
| 产品形态 | 单机桌面软件（PySide6），本地 SQLite 存储，无需联网、无需服务端 |
| 面向市场 | 中国大陆工商业分布式光伏（含余电上网与全额上网边界情形） |
| 在项目流程中的位置 | 项目前期踏勘后的方案测算与投资评审环节，服务于可行性研究，不替代设计软件与调度系统 |
| 与通用工具的区别 | 通用表格工具不强制数据口径与单位一致性；CENEP 把业务规则固化为代码与校验，错误输入会被拒绝而不是被静默修正 |
| 数据权威性 | 本项目当前**不包含**任何已核实的全国电价数据；一切电价数据必须由使用者按来源录入并标注来源 |

### 1.3 适用范围

- 工商业分布式光伏项目的用电侧消纳分析（自发自用、余电上网、电网购电）。
- 项目基础信息的登记、维护与本地归档。
- 输入数据的完整性、单位一致性、时间粒度一致性校验与问题清单输出。
- （后续版本）电费账单导入、负荷与分时电价分析、发电量模拟、经济评价与方案对比。

### 1.4 明确的不适用范围

- 不做光伏电站的电气设计、选型计算与施工图，不输出设计图纸。
- 不做电站的实时运行监控、数据采集与远程运维。
- 不做电网调度、电力市场报价与交易执行。
- 不做财务记账与税务申报，或替代会计师事务所的审计工作。
- 当前版本不做任何财务状况、收益水平、投资回收能力的结论性输出：完整财务模型尚未实现。

## 2. 用户角色

### 2.1 光伏项目开发 / 设计人员

| 项目 | 说明 |
|---|---|
| 使用场景 | 现场踏勘后，把业主提供的台账与负荷信息登记入软件，先判断装机容量与消纳水平的匹配度，再决定是否深入做方案 |
| 关注指标 | 总用电量、总发电量、自用电量、自用率、余电比例、负荷覆盖率 |
| 当前可用能力 | 登记项目基础信息；用时段电量序列试算不同装机规模下的消纳结果，快速看自用率与余电比例的变化 |
| 当前不可用能力 | 自动获取电价、账单自动解析、发电量模拟、财务测算 |
| 主要痛点 | 现场只有月度账单，缺少逐时曲线，需要先知道"用月度数据能判断到什么程度" |

### 2.2 工商业业主能源管理人员

| 项目 | 说明 |
|---|---|
| 使用场景 | 评估自家屋顶光伏能省多少电费、会不会影响生产用电，需要一个能向管理层解释的测算依据 |
| 关注指标 | 自用电量、负荷覆盖率、可避免的购电成本、基本电费与需量电费是否变化 |
| 当前可用能力 | 查看项目信息；按自身典型日负荷与发电曲线核对消纳水平 |
| 当前不可用能力 | 电费账单导入、分时电价套算、需量电费分析、收益结论 |
| 主要痛点 | 不清楚"省的电"到底按哪个电价计价，容易被平均电价误导 |

### 2.3 咨询与设计院技术人员

| 项目 | 说明 |
|---|---|
| 使用场景 | 为多个业主项目做批量测算，需要统一的测算口径、可复算的输入记录与可交付的测算说明 |
| 关注指标 | 计算规则版本、假设版本、输入指纹、数据来源与精度等级、校验问题清单 |
| 当前可用能力 | 通过命令行 `python -m cenep.cli` 批量做消纳试算并输出 JSON（含 `calculation_version` 与 `input_fingerprint`） |
| 当前不可用能力 | 报告导出（Excel / PDF）、方案对比报告、电价库管理 |
| 主要痛点 | 不同人用不同口径算，结果无法比对；缺少把口径写进交付物的手段 |

### 2.4 投资方评审人员

| 项目 | 说明 |
|---|---|
| 使用场景 | 复核开发方提交的测算，重点检查输入数据是否真实、口径是否一致、结论是否有假设支撑 |
| 关注指标 | 数据来源类型（实测 / 账单分摊 / 模拟 / 人工）、校验状态、假设版本、规则版本 |
| 当前可用能力 | 查阅项目的输入与计算规则版本信息，核对消纳计算是否按逐时段口径执行 |
| 当前不可用能力 | 现金流与收益率复核、敏感性分析、报告交叉比对 |
| 主要痛点 | 拿到的是一堆数字，看不到数字背后的假设与数据等级 |

## 3. 典型使用流程

以下为端到端流程。每条末尾标注当前版本 `0.1.0` 的执行状态：
**已可执行** = 现在就能做；**尚未开放** = 计划在后续版本提供，当前点击无效属预期行为。

1. **启动软件**：运行 `python -m cenep`、`python -m cenep.cli gui` 或安装后的 `cenep-gui` 脚本。
   状态：**已可执行**。无图形环境时可用 `python -m cenep.cli info` 查看版本与运行环境。
2. **登记项目**：填写项目名称（必填）、项目地址、业主/客户、项目类型、项目说明。
   状态：**已可执行**。名称空白会在对话框与领域校验两层被拒绝。
3. **落库并核对**：保存后项目真实写入本地 SQLite，列表从数据库重新加载（不使用内存假数据）。
   状态：**已可执行**。数据库默认位于 `%LOCALAPPDATA%\CENEP\cenep.db`，可用 `CENEP_DB_PATH` 覆盖。
4. **登记原始资料**：导入电费账单 PDF/图片/Excel 与负荷数据文件，形成 `Document` 记录并保留原始文件。
   状态：**尚未开放**（第二阶段）。当前只能把账单中的关键数字人工整理为时段电量序列备用。
5. **提取账单数据**：解析月度用电量、电费金额、账期，形成 `BillRecord` 并标注校验状态。
   状态：**尚未开放**（第二阶段）。
6. **建立负荷曲线**：导入电表分时计量数据，或按典型曲线把月度电量分摊为估算曲线，并明确标注来源类型。
   状态：**尚未开放**（第三阶段）。
7. **建立电价方案**：录入地区、生效日期、适用用户类型、来源说明与分时电价时段，形成 `TariffModel`。
   状态：**尚未开放**（第三阶段）。
8. **执行消纳计算**：输入各时段用电量（kWh）与光伏发电量（kWh），声明时段长度（分钟），计算自用、上网、购电电量与三个比例指标。
   状态：**已可执行**。输入不合规（长度不一致、负数、NaN、无穷、非数值、时段长度非法）会返回结构化问题清单并拒绝计算，原始数据不被修改。
9. **查看结构化结果**：界面或命令行展示五个电量指标、三个比例指标、状态、输入指纹、计算规则版本与业务提示。
   状态：**已可执行**。零分母的比例指标显示为"未定义"，不会显示为 0。
10. **留存计算留痕**：把本次计算登记为 `CalculationRun`（含输入快照与计算版本），指标写入 `ResultRecord`。
    状态：**尚未开放**。当前计算结果只在界面与命令行输出，未落库。
11. **套用电价测算收益**：按逐时段对应的购电边际成本计算自用收益，并单独判断基本电费与需量电费。
    状态：**尚未开放**（第三阶段）。
12. **模拟发电量**：按容量、倾角、方位、组件与逆变器参数模拟逐时发电量。
    状态：**尚未开放**（第四阶段）。
13. **经济评价**：计算初始投资、运维费用、现金流、净现值、内部收益率与投资回收期。
    状态：**尚未开放**（第五阶段）。
14. **方案对比与报告输出**：对比多套装机与电价组合，导出 Excel / PDF 报告。
    状态：**尚未开放**（第六阶段）。

当前版本可闭环的部分是第 1 至 3 步与第 8 至 9 步；第 4 至 7 步与第 10 至 14 步尚未开放。

## 4. 功能边界

### 4.1 已实现（版本 `0.1.0`，有测试覆盖）

| 功能 | 实现位置 | 说明 |
|---|---|---|
| 项目基础信息新增 | `ProjectService.create_project` | 名称/地址/业主/类型/说明，写入 SQLite |
| 项目基础信息查询 | `list_projects` / `get_project` / `find_project` | 列表按更新时间倒序，另有按名称精确查询 |
| 项目基础信息修改 | `update_project` | 只覆盖显式传入字段，自动刷新 `updated_at` |
| 项目基础信息删除 | `delete_project` | `RESTRICT` 策略：存在关联数据时拒绝删除 |
| 数据真实持久化 | `src/cenep/infrastructure/database.py` | 参数化 SQL、外键开启、事务回滚、WAL |
| 全量数据表结构冻结 | `SCHEMA_STATEMENTS` | 11 张业务表与索引一次性建好，模式版本 `1` |
| 逐时段消纳计算 | `calculate_self_consumption` | 自用 `min(load, pv)`、上网 `max(pv-load, 0)`、购电 `max(load-pv, 0)` |
| 比例指标与零分母处理 | 同上 | 自用率、负荷覆盖率、余电比例；零分母返回"未定义"而非 0 |
| 能量守恒自检 | `SelfConsumptionResult.check_energy_balance` | 容差 `1e-9` kWh，不满足即抛错 |
| 结果可追溯 | 同上 | `calculation_version`、`assumptions_version`、`input_fingerprint`（SHA-256 前 16 位） |
| 输入校验与结构化问题清单 | `src/cenep/domain/validation.py` | 稳定问题代码（`length_mismatch`、`negative_value`、`nan_value`、`infinite_value`、`not_a_number`、`not_a_sequence`、`interval_minutes_invalid`），带严重程度与原始值 |
| 数据质量业务提示 | `classify_energy_series` | 空数组、全零、无光伏、无负荷四类提示，不影响数值 |
| PySide6 桌面界面 | `src/cenep/ui/main_window.py` | 项目列表增删改查、消纳计算输入与结果展示、当前阶段状态区 |
| 未开放功能的显式声明 | `NOT_IMPLEMENTED_FEATURES` | 界面直接列出尚未开放的功能，避免误以为可用 |
| 命令行入口 | `src/cenep/cli.py` | `init-db` / `project-add` / `project-list` / `project-show` / `project-update` / `project-delete` / `self-consumption` / `gui` / `info`，支持 `--json` 输出 |
| 数据库路径可配置 | `src/cenep/config.py` | 参数 > 环境变量 `CENEP_DB_PATH` > `%LOCALAPPDATA%\CENEP\cenep.db` |
| 自动化测试 | `tests/`（244 个用例全部通过） | 含分层隔离、界面无业务公式、无占位实现等架构守卫测试 |

### 4.3 明确不做

| 不做的事 | 原因 |
|---|---|
| 电气设计、选型计算与施工图输出 | 属设计软件职责，CENEP 只做经济评价 |
| 实时运行监控与远程运维 | 属监控平台职责，需要现场通信与长期在线服务 |
| 电网调度与电力市场报价执行 | 属交易系统职责，且涉及资质与合规 |
| 财务记账与税务申报 | 属财务软件职责，CENEP 只做项目评价测算 |
| 自动判定"项目是否可行" | 决策依据必须由使用者结合边界条件判断；软件只提供口径正确的指标 |
| 用单一平均电价替代分时电价给出收益 | 违反业务规则，会系统性高估或低估自用收益 |
| 把年度总用电量与总发电量直接相除给出自用率 | 抹掉时序匹配关系，结论不可靠 |
| 把月度数据当作逐时曲线参与逐时消纳计算 | 属于口径混用，必须标注数据精度等级 |
| 把未核实来源的电价数据标记为已核实正式电价 | 破坏数据证据等级，误导评审 |
| 在核心计算路径上留下占位实现 | 已有自动化测试禁止 `NotImplementedError` 与空实现函数 |

## 5. 业务优先级

| 优先级 | 事项 | 理由 |
|---|---|---|
| P0 | 项目基础信息完整 CRUD | 全部业务数据的隔离边界，没有项目就没有后续一切数据归属 |
| P0 | 逐时段消纳计算 | 经济评价的电量基础；口径错了，后面所有金额都错 |
| P0 | 输入校验与结构化问题清单 | 拒绝静默修正是不返工的前提；问题要能定位到字段与时段 |
| P0 | 数据真实持久化与事务安全 | "算完就丢"无法支撑评审；关联数据删除必须可拒绝 |
| P0 | 电费账单导入与关键字段提取 | 真实项目的输入源头；没有账单数据，评价只能停在示例 |
| P0 | 完整财务现金流与税务模型 | 投资方评审的核心诉求；缺此则产品无法交付评价结论 |
| P1 | 负荷曲线与来源精度标注 | 决定消纳结果精度；但允许先用估算曲线推进 |
| P1 | 分时电价模型与逐时段收益 | 自用收益的正确算法依赖它；可与账单导入并行推进 |
| P1 | 光伏发电量模拟 | 可从外部导入发电量曲线过渡，故排在财务模型之后 |
| P1 | 方案对比与报告导出 | 交付物形态；依赖前面的测算能力成型 |
| P2 | 屋面识别、自动排板与三维展示 | 显著提升体验但投入大，不阻塞经济评价主链路 |
| P2 | 储能充放电优化 | 只在配储方案下需要，属增值能力 |
| P2 | 电力市场交易优化 | 依赖地区市场规则与政策演进，成熟度不足 |
| P2 | 用户权限与云端协同 | 单机离线场景已覆盖多数目标用户；协同属规模化能力 |
| P2 | 安装包制作 | 开发者可直接运行；面向非技术用户分发时才成为刚需 |

## 7. 关键业务约束

以下 12 条为已冻结的业务规则。它们约束后续所有电量、电价与财务功能的设计与实现方式。

| 序号 | 约束 | 对产品的实际影响 |
|---|---|---|
| 1 | 月度电量数据不能等同于逐时负荷曲线 | 月度账单录入后只能作为整月累计值存储；界面与结果必须显示该数据无法支撑逐时消纳，需要额外数据才能升级精度 |
| 2 | 月度估算与逐时消纳计算必须区分 | 两类结果使用不同的结果标识与来源标注，同名指标不得混用；报告中对估算结果必须附加说明 |
| 3 | 逐时消纳要求负荷与光伏在相同时间粒度、相同计量边界 | 校验层强制两个序列长度一致；程序不做重采样，粒度不同的数据必须由调用方先归一再输入；`interval_minutes` 只是声明值 |
| 4 | 不能仅凭年度总用电量和年度总发电量推出可靠自用率 | 产品不提供"年度总量相除得自用率"的功能入口；若用户提供年度数据，只能标注为粗略参考值 |
| 5 | 光伏自用收益应按对应时段真正可避免的购电边际成本测算 | 电价套算必须逐时段对齐；平均电价只能用于展示对比，不能用于收益计算 |
| 6 | 基本电费/需量电费/功率因数调整及其他费用不得默认按用电量同比减少 | 费用结构在结果中单列，容量与需量类费用默认不变，需使用者结合合同与需量曲线单独判断 |
| 7 | 峰谷电价必须考虑时段对应关系 | 电价方案必须包含时段划分；不允许用简单年平均电价替代分时电价参与计算 |
| 8 | 电价数据必须具有地区、生效日期、适用用户类型和来源 | `TariffModel` 强制记录 `region`、`effective_from`/`effective_to`、`tariff_type`、`source_reference`；四要素不全的方案只能保持草稿状态 |
| 9 | 未经正式来源核实的湖北电价数据不得标记为已核实正式电价 | `source_reference` 为空的数据不得置为启用状态；软件当前不内置任何已核实电价，全部电价须由使用者录入并注明来源 |
| 10 | 缺失数据、估算数据和正式数据必须区分 | 缺失值以空值表达，禁止填 0 或填估算值冒充实测值；数据质量等级贯穿导入、校验、计算与报告 |
| 11 | 计算结果必须可追溯到输入与规则版本 | 每次结果记录计算规则版本、假设版本与输入指纹；历史结果按当时的版本解释，不得用新口径重新解释旧结果 |
| 12 | 校验不得静默修正原始数据 | 越界、缺失、量纲可疑的数据一律拒绝并列出问题，由使用者修正后重算；程序不截断、不补齐、不取绝对值 |

## 8. 非功能需求

| 需求 | 具体要求 | 落实方式 |
|---|---|---|
| 数据可追溯 | 任何结果都能回答"用哪份输入、按哪版规则算的" | 计算规则版本与假设版本常量、输入指纹、`CalculationRun.input_snapshot` 表结构 |
| 项目间数据隔离 | 不同项目数据不得互相污染，不存在跨项目聚合 | 每张业务表带 `project_id` 外键；`RESTRICT` 删除策略；项目是唯一隔离边界 |
| 离线可用 | 无网络环境可完整使用；不依赖服务端 | 本地 SQLite 存储；无网络请求依赖；架构测试禁止在核心层引入网络与 PDF/OCR 库 |
| Windows 可安装可运行 | 在 Windows 上可安装、可启动、可操作、可保存、可退出 | `pyproject.toml` 定义 `cenep-gui` 与 `cenep` 入口；`python -m cenep` 与 `python -m cenep.cli` 双入口；PySide6 缺失时给出明确提示而非静默失败 |
| 计算与界面解耦 | 计算逻辑不依赖图形界面、数据库与第三方数据处理库 | 依赖方向固定为 表现层 → 应用服务层 → 领域层；基础设施层由应用服务层调用；`tests/unit/test_layering.py` 自动检查越界导入 |
| 测试覆盖要求 | 核心计算、校验规则、持久化、界面装配均有测试；新增能力必须同步补测试 | 当前 244 个用例全部通过；含能量守恒、边界情形、分层隔离、界面无业务公式、无占位实现等检查 |
| 单位与量纲一致性 | 电量单位统一 kWh、金额统一元、容量单位 kWp；时段电量与瞬时功率字段名显式区分 | 字段命名强制 `energy_kwh` / `power_kw`；界面与命令行标签直接写明单位 |
| 数据安全 | 不泄露本地绝对路径到业务记录；关联数据删除必须被安全策略拦截 | `Document.filename` 只存文件名；删除走 `RESTRICT`，由数据库拒绝而非应用层猜测 |
| 可维护性 | 单个源文件不得过度膨胀，分层目录必须真实包含实现 | 架构测试限制单文件不超过 1200 行，并检查五个分层目录均有实现文件 |

## 9. 术语表

| 术语 | 定义 | 在本软件中的对应 |
|---|---|---|
| 时段电量 | 某一时间区间内累计的电量，单位 kWh | `LoadProfile.energy_kwh`；消纳计算的输入序列 |
| 瞬时功率 | 某一时刻的功率，单位 kW | `power_kw` 命名的字段；**不得**作为时段电量输入计算 |
| 消纳 | 光伏出力被同计量边界内的负荷直接使用的过程与结果 | `calculate_self_consumption` 的逐时段拆分 |
| 自用率 | 自用电量 ÷ 光伏发电量，取值 0~1；光伏发电量为 0 时未定义 | `self_consumption_rate` |
| 负荷覆盖率 | 自用电量 ÷ 用电量，取值 0~1（逐时段取小后求和，不会超过 1）；用电量为 0 时未定义 | `load_coverage_rate` |
| 余电比例 | 余电上网电量 ÷ 光伏发电量，取值 0~1；光伏发电量为 0 时未定义 | `export_rate` |
| 余电上网 | 光伏出力超出同时段负荷的部分送入电网，即 `max(pv - load, 0)` | `total_export_kwh` |
| 电网购电 | 同时段负荷超出光伏出力的部分由电网补充，即 `max(load - pv, 0)` | `total_grid_import_kwh` |
| 分时电价 | 按峰、平、谷等时段分别定价的电价体系 | `TariffType.TOU_INDUSTRIAL`；电价方案必须带时段划分 |
| 需量电费 | 两部制电价中按最大需量（kW）计收的基本电费部分，与用电量无关 | `TariffType.DEMAND`；不随光伏发电量同比减少，需单独判断 |
| 计量边界 | 电量的计量位置与口径，例如同一并网点、同一关口表 | 逐时消纳的前提条件之一，与时间粒度共同约束输入 |
| 基本电费 | 两部制电价中按变压器容量或合同需量计收的固定费用部分 | 费用结构单列，不默认按发电量扣减 |
| 功率因数调整电费 | 因功率因数偏离考核标准而产生的奖励或罚金 | 属"其他费用"，不得默认随光伏发电量变化 |
| 自用收益 | 自用电量按对应时段可避免的购电边际成本折算的收益 | 第三阶段实现；按逐时段电价计算，禁用年平均电价 |

## 10. 变更管理

本文件与 `docs/CALCULATION_SPEC.md`、`docs/ROADMAP.md` 同步维护。任何改变产品范围、功能边界或业务约束的改动，必须同时：

1. 更新本文件对应章节；
2. 若涉及计算口径，按 `docs/CALCULATION_SPEC.md` 第 11 节提升计算规则版本与假设版本；
3. 更新 `docs/ROADMAP.md` 中受影响阶段的目标、交付物与验收门槛；
4. 在 `tests/` 中补充或更新测试，并实际运行 `python -m pytest -q` 确认全部通过。
