## 3. 实现过程中发现并修复的真实排版问题

以下每一条都由真实账单（或忠实还原其排版的夹具）**实际触发**，
并已固化为回归用例：

| # | 现象 | 后果 | 处理 |
|---|---|---|---|
| 1 | 标签内含电压等级数字（`用电户-110千伏-…-35千伏`） | 会取到 `-110`/`-35` 作为金额 | 跳过"数字+参数单位"结构；参数单位与金额/电量单位分开枚举 |
| 2 | `千瓦时` 以 `千瓦` 开头 | 电量被误判为功率参数而整条丢弃 | 单位识别改为**最长优先匹配** |
| 3 | 小数位与小数点被换行切开（`1787644.` ⏎ `3`） | 金额截断 | 解析前拼接被切开的数值 |
| 4 | `0.76297` 被匹配成 `0` | 平均电价变成 0 | 数值正则**先匹配带小数形态** |
| 5 | 同一行的数量与金额相邻（`8780498 6708448.31`） | 两者混淆 | 按量纲（kWh / 元）分流 |
| 6 | 标签与数值被换行分隔 | 取不到值 | 逐行数值区扫描 |
| 7 | 一个数值跨两行（`…为-9206.37` ⏎ `元，…`） | 单位缺失被判"单位不明" | 仅在行尾可能被切断时借用下一行补全 |
| 8 | 公式行 `3.工商业电费=(1)…+(5)…` | `(1)`/`(5)` 被当成金额或负号 | 排除口径说明行；跳过被括号包住的短整数 |
| 9 | 备注行 `5.根据《…》[2023]163号` | 行首编号与文号被当成金额 | 排除行首编号与引用/说明行 |
| 10 | 同一数值被复述两次（功率因数调整电费） | 误判为冲突 | 同一页内**按数值**去重 |
| 11 | 相邻字段在同一窗口（`需量电费` 后紧跟 `平均电价0.76297`） | 假冲突 | 窗口在标签所在数值块内截断 |
| 12 | 单位只写在表头，数值无单位 | 若强制要求单位会全部取不到 | 优先带单位者；仅当窗口内无单位数值时才采纳裸数值；带**未知单位**一律交人工复核 |

**最重要的两条（任务书明确要求）**：

- **不得把标签后的第一个数字当金额**（问题 1、8、9）；
- **正式总用电量只取权威字段**，不得由计量点或分时电量求和（问题 5 及相关用例）。

## 4. 与任务书约束的对应关系

| 约束 | 落实情况 |
|---|---|
| 金额使用 `Decimal`，不用 `float` 运算/比较 | 模型层拒绝 `float`；`test_amounts_are_decimal_not_float`、`test_float_tolerance_rejected`、源码扫描用例 |
| 缺失值为 `None`，不补 0 | `FieldStatus.MISSING` 强制 `value is None`；多处以 `!= Decimal(0)` 断言 |
| 多候选冲突不得静默选值 | `needs_review` 强制 `value is None`；`test_conflict_*`（含"不得取首个/最大/最小"） |
| 正式总用电量只取权威字段 | 权威标签白名单 + 计量点行排除；`test_total_consumption_not_summed_from_metering_points`、`test_total_consumption_never_summed` |
| 标签内含电压等级数字时不得识别为金额 | `test_industrial_commercial_fee_not_first_number_after_label` 明确断言不等于 `-110`/`-35` |
| 勾稽超差只告警、不改原始数据 | `ReconciliationResult.to_issue()` 生成 `WARNING`；`test_reconciliation_exceeds_tolerance_warns`、`test_reconciliation_does_not_modify_original_amounts` |
| 不把账单展示平均电价当作光伏边际节省电价 | 该字段独立保存、单位 `元/kWh`；`test_average_price_unit_is_price_not_amount`、`test_average_price_not_overwritten_by_recomputed` |
| 提取不完整或账单未确认时不得进入正式测算 | `BillFieldSet.is_usable_for_calculation` 要求 `extraction_status is SUCCESS`；`test_partial_extraction_not_usable_for_calculation` 等 5 例 |
| 不把真实账单文件或客户标识提交到公开仓库 | 仓库内无 PDF；夹具为脱敏最小片段；`test_fixture_contains_no_customer_identifiers`、长编号扫描用例 |

## 5. 功能限制与遗留风险

### 5.1 本批次**未实现**（有意留到后续子任务）

1. **费用明细的完整字段**：仅解析 5 个费用分项 + 功率因数调整 + 需量电费；
   账单中还有辅助服务费用、抽水蓄能容量电费、煤电容量电费等细项，**未解析**。
2. **分时电量与电价**（P0-3）：尖峰/峰/平/谷电量、直接交易电价、分时明细未解析。
3. **计量点明细**（第 2 页）：正向有功/无功、最大需量、倍率、变损线损等未解析。
4. **数据库落库**（P0-4）：本批次**不写数据库**，`SCHEMA_VERSION` 未改，
   现有 `BillRecord` 表结构未动。
5. **人工复核界面**（P0-5）：`needs_review`/`missing` 只产出结构化状态，
   尚无界面呈现与确认入口。
6. **OCR**：本阶段明确不做。

### 5.2 已知限制

1. **单位纪律是"窗口内判断"**：当某字段窗口内**没有任何**带单位数值时，
   会选择裸数值（因真实账单常把单位写在表头）。若该行恰好混入同量纲的
   异义数值，仍可能取错——已通过"数值块截断"降低风险，但**不是绝对保证**。
   凡是存在多个不同候选的情形都会进入人工复核。
2. **标签覆盖有限**：规则基于两份真实账单（国网湖北、110kV 大工业用电）的
   标签集。**其他省份/电压等级/用电类别的账单版式未验证**，
   很可能出现标签不匹配（表现为 `missing`，而非取错值）。
3. **`duplicate` 状态未接入**：内容哈希去重属应用层，本批次未涉及。
4. **只有两份账单做过字段级验证**：2025-01～08 共 8 份账单**未核验字段值**。
5. **未做模糊测试**：超大/恶意/加密 PDF 未验证（该路径在 P0-1 已判 `failed`）。
6. **`is_usable_for_calculation` 为 `True` 不代表账单已确认**——
   是否确认由用户决定（P0-5），解析成功 ≠ 账单有效。

### 5.3 后续建议

1. 合并本 PR 后进入 P0-3（分时电量与电价），复用同一证据模型。
2. 入库前（P0-4）需评估金额列精度：现有 `BillRecord` 金额列为 `REAL`，
   而解析全程使用 `Decimal`；直接落 `REAL` 会引入浮点误差，建议改为
   十进制安全存储（整数分或十进制字符串），该决策在 P0-4 设计时给出。
3. 用其余 8 份真实账单扩充字段级验证，并逐步把夹具从"两份"扩到"更多版式"。
